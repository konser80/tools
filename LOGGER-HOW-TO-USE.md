logger - модуль логирования (обвязка на log4js)

# Как использовать в проектах

Setup:
npm i konser80/tools

Usage:
const logger = require('./logger');
const log = logger('trace', { dir: 'logs', hourly: false });

log.trace(somedata, opts);
log.debug(somedata);

Important:
Функция принимает лишь один аргумент для вывода, поэтому log.trace(arg1, arg2, arg3) не сработает.

# console.*

После configureLogger() все console-методы (log, info, debug, warn, error) идут через логгер и попадают в файлы: console.log → trace, console.info и console.debug → debug, console.warn → warn, console.error → error. Отдельно настраивать ничего не нужно.

# Завершение процесса

Важно: log4js пишет в файлы асинхронно. Обычный process.exit() убивает процесс до того, как строка доедет до диска — в консоли она видна, а в error.log её нет. Ровно та строка, ради которой лог и заводят (fatal перед смертью), теряется чаще всего.

Поэтому process.exit(code) заменяем на:

log.exit(code);

Именно заменяем, а не дописываем рядом. log.exit() асинхронен: он возвращает управление сразу, флаш ещё даже не начался. Поэтому

log.exit(1);
process.exit(1);   // <- строка теряется ровно как раньше

не даёт ничего: process.exit() выполнится синхронно и убьёт процесс посреди флаша. Выглядит как защита, которой нет.

log.exit() ничего не перехватывает и не ставит обработчиков — он завершает процесс ровно там, где раньше стоял ваш process.exit(), и с тем же кодом. Весь его код: shutdown(() => process.exit(code)) плюс флаг от повторного вызова.

Он дожидается флаша и только потом завершает процесс. Вызов идемпотентный: если exit() дёрнули дважды, побеждает первый — второй не оборвёт незаконченную запись. Если log4js не ответил за 3 секунды (например, диск полон), процесс всё равно завершится, а не повиснет.

После log.exit() логировать бессмысленно: log4js отключает запись, и строки пропадут и из файла, и из консоли (console.* перенаправлены в logger). log.exit() должен быть последним действием.

Обработчики сигналов и падений ставит сам проект — библиотека в них не вмешивается:

process.on('SIGINT', () => log.exit(0));
process.on('SIGTERM', () => log.exit(0));   // pm2 restart шлёт SIGINT
process.on('uncaughtException', (err) => { log.fatal(err); log.exit(1); });

Если нужен не выход, а просто дождаться записи (например, перед долгой паузой), есть log.shutdown():

await log.shutdown();          // промис
log.shutdown(() => { ... });   // или колбэк

Форма log.shutdown(() => process.exit(code)) тоже дописывает файл и оставляет process.exit на виду, но в точках выхода она хуже: у неё нет защиты от двойного вызова. Если выход инициировали две точки почти одновременно (crash-хендлер и обработчик сигнала — обычное дело при падении под pm2), второй shutdown завершится синхронно, потому что аппендеров у log4js уже нет, и его process.exit оборвёт первый флаш. Строка снова потеряется. У log.exit() побеждает первый вызов, поэтому в точках выхода используем его.

# Чистка старых логов

Ротированные логи складываются в <dir>/<prefix>trace.old/YYYY-MM/ и <dir>/<prefix>error.old/ и по умолчанию лежат там вечно. Встроенная чистка log4js (numBackups) тут не работает: она ищет старые файлы только в самой <dir> и в подпапки не заглядывает.

Чтобы логгер чистил их сам, добавьте keep:

const log = logger('trace', { dir: 'logs', keep: '30d' });

Раз в сутки из этих двух папок удаляются *.log старше указанного возраста (по mtime), опустевшие папки месяцев тоже убираются. Активные trace.log и error.log лежат в корне <dir>, в папки ротации не попадают и не трогаются никогда. Файлы других расширений, если их туда положить, тоже переживут чистку.

Без keep не удаляется ничего — сама по себе чистка не включается.

keep — это возраст, а не количество: если логов много, но все свежие, не удалится ни один. Потолка по размеру папки нет.

Первая чистка происходит через сутки после старта, а не при запуске. Папок, которых ещё нет (ротации не было), чистка не создаёт. Таймер unref-нутый: процессу, который закончил работу, он не мешает завершиться. Ошибка чистки (нет прав, отвалился диск) уходит в log.warn и процесс не роняет.

Выключить: log.stopPurge().

# Когда какие методы применять

Аналогия: log.info() — это H1 на странице (редкие, важные события), log.debug() — H2 (основной поток), log.trace() — H3 (детали и сырые данные).

## trace

log.trace(raw) - это "нижний" уровень. Его можно вызвать перед вызовом "долгой" функции (например, перед внешним API запросом). Также через него можно логировать сырой ответ.
В консоль выводится синим цветом.

## debug

Через log.debug() стоит выводить результат действия уже отформатированный. Этот метод используем в большинстве случаев.
В консоль выводится серым цветом.

## info

log.info() используем для важных событий. Например - прилетел webhook или инициирован новый pipeline.
В консоль выводится белым цветом.

## warn, error

log.warn(), log.error() - стандартное использование.

Важно: в log.warn() и log.error() НЕ нужен префикс '[-]' — эти уровни сами выводят крупный контрастный бейдж (жёлтый ' W ' / красный ' E '). Префиксы [ ], [·], [+], [-] используем только в trace/debug/info.

# Best Practice

logger сам выводит datetime с милисекундами.

## task number & task status

Если в проекте это уместно - хорошей практикой я считаю каждой задаче назначать taskId (начиная с 000, далее делать taskId % 1000).

Также использовать префиксы информационные, для начала задачи, для успешного выполнения и неуспешного: [ ], [·], [+], [-]

Примеры вывода:

log.trace(`[ ][${task}] command received: getRate`);
log.trace(`[·][${task}] fetching data from url ${url}`);
log.trace(`[-][${task}] proxy ${proxy.url} failed, skipping`);
log.trace(`[+][${task}] fetched 16kb in 0.3 sec`);
log.debug(`[+][${task}] getRate: RUB=78.3, EUR=1.17`);
